# 대학알리미 API 수집기 설계 및 이행 계획

## 1. 목적

대학알리미 Open API 9개 서비스의 검증된 103개 기능을 연도·학교·지역 범위에 맞게
계획하고, 원본 XML을 재현 가능하고 중단 후 재개 가능한 방식으로 수집한다. 수집기는
분석용 정제 데이터를 만드는 도구가 아니라 변경하지 않은 원본과 그 출처·무결성 정보를
확보하는 첫 단계다.

2025년 기준 학교코드 377개를 적용하면 17,431개 작업이 생성된다. 학교 수가 달라지는
연도에는 학교별 작업 수가 함께 달라진다.

## 2. 설계 목표와 비목표

### 목표

- 설정 파일만으로 103개 기능의 요청 범위와 고정 파라미터를 설명한다.
- 인증키를 파일명, 로그, 예외, manifest에 노출하지 않는다.
- HTTP 성공뿐 아니라 API 결과코드, 전체 건수, 실제 행 수와 응답 필드를 검증한다.
- 원본을 덮어쓰지 않고 SHA-256으로 동일성과 변조 여부를 확인한다.
- 중단 후 같은 명령을 실행하면 정상 완료 작업은 네트워크 요청 전에 건너뛴다.
- 학교·캠퍼스·학과 식별자의 앞자리 0을 보존한다.
- 실제 응답의 중복과 필드 구성을 삭제하거나 보정하지 않고 측정해 기록한다.

### 비목표

- XML을 분석용 패널 테이블로 변환하거나 결측값을 대체하지 않는다.
- 추정한 의미키의 유일성을 수집 단계에서 강제하지 않는다.
- 확인되지 않은 자동 페이지 분할이나 무제한 동시 요청을 사용하지 않는다.
- 공공데이터포털의 대학알리미 외 유사 API를 자동으로 범위에 추가하지 않는다.

## 3. 구성과 책임

| 구성 | 경로 | 책임 |
|---|---|---|
| 기능 명세 | `config/academyinfo/endpoints.yaml` | 서비스·기능·범위 전략·입출력 필드·고정 파라미터 정의 |
| 실행 정책 | `config/academyinfo/runtime.yaml` | 동시성, 제한시간, 단일 응답 허용 행 수 정의 |
| 작업 계획 | `src/academyinfo/planning.py` | 설정과 연도·학교 목록을 결정적 수집 작업으로 변환 |
| 다운로드 | `src/academyinfo/downloader.py` | 인증키 주입, 재시도, 디스크 스트리밍, XML 프로파일링 |
| 수집 조정 | `src/academyinfo/collection.py` | 학교 탐색, 검증, 동시 실행, 오류 격리 |
| 원본 저장 | `src/academyinfo/storage.py` | 무덮어쓰기 저장, manifest, 체크섬, 재시작 처리 |
| CLI | `scripts/collect_academyinfo.py` | 사용자 입력 검증과 전체 흐름 실행 |

수집 흐름은 다음과 같다.

1. 연도별 `getUniversityCode` 전체 응답을 받아 학교코드 집합을 확정한다.
2. 기능별 범위 전략과 고정 파라미터를 결합해 결정적 작업 ID를 만든다.
3. manifest와 원본 파일의 크기·SHA-256을 검사해 완료 작업을 먼저 제외한다.
4. `numOfRows=1` 탐색 요청으로 `totalCount`를 확인한다.
5. 전체 건수가 1보다 크면 그 건수를 `numOfRows`로 지정해 전체 XML을 받는다.
6. 응답 계약과 무결성을 검사한 뒤 원본을 원자적으로 게시한다.
7. 출처, 요청 범위, 응답 특성, 파일 크기와 SHA-256을 manifest에 추가한다.

## 4. 작업 계획

수집 작업은 서비스, 기능, URL, 범위 전략과 비밀이 아닌 요청 파라미터를 정규화한 뒤
SHA-256 기반 `task_id`로 식별한다. 입력 순서가 달라도 같은 논리 작업은 같은 ID를 갖고,
요청 의미가 바뀌면 다른 ID를 갖는다.

| 범위 전략 | 생성 단위 | 2025년 작업 수 |
|---|---|---:|
| `per_school_by_year` | 학교 × 연도 | 17,342 |
| `regional_by_school_type` | 학교구분 | 64 |
| `nationwide_by_year` | 연도 | 5 |
| `lookup_by_year` | 연도 | 4 |
| `lookup_once` | 기능당 1회 | 15 |
| `regional_all_school_types` | 기능당 1회 | 1 |

기능 자체가 요구하는 `indctId`나 빈 `schlKrnNm` 같은 값은 코드의 기능명 분기가 아니라
각 기능의 `fixed_params`에 둔다. 범위 파라미터와 충돌하거나 인증정보로 보이는 키는 계획
단계에서 거부한다.

## 5. 다운로드와 요청 정책

- 기본 동시 요청은 2개이고 검증된 상한은 4개다.
- 연결 오류와 일시적 전송 오류는 제한된 횟수로 재시도한다.
- 응답은 메모리에 모두 적재하지 않고 임시 파일로 스트리밍한다.
- 탐색 응답의 `totalCount`가 70,000행을 넘으면 자동 분할하지 않고 검토를 요청한다.
- 탐색 후 전체 요청에서는 `totalCount`가 바뀌지 않았는지 다시 확인한다.
- 현재 페이지 분할은 기능별 검증이 끝나기 전까지 비활성화한다.

인증키는 최종 URL 구성 시점에만 주입한다. 다운로드 오류는 URL 쿼리나 인증키를 포함하지
않는 안전한 오류 유형과 시도 횟수만 상위 계층에 전달한다.

## 6. 응답 검증 계약

모든 응답은 다음 조건을 만족해야 저장된다.

- HTTP 상태가 200이다.
- API `resultCode`가 `00`이다.
- `totalCount`가 숫자이고 탐색·전체 요청 사이에 일치한다.
- 실제 `item` 수가 요청 정책상 예상한 행 수와 일치한다.
- 실제 필드가 기능 설정의 `output_fields`에 선언된 필드의 부분집합이다.

대학알리미 XML은 값이 없는 선택적 필드의 태그를 생략한다. 따라서 선언된 모든 필드가
매 응답에 반드시 등장해야 한다고 강제하면 정상 응답을 실패로 오판한다. 2026-09-14
실수집에서 `getUniversityMajorCode`, `getOrdmthEdcCrseInstOper` 등의 선택적 설명·지표
필드가 생략되는 사례를 확인했고, 수집기는 다음 원칙으로 수정했다.

- **선언됐지만 응답에 없는 필드**: 허용하고 실제 등장 필드만 manifest에 기록한다.
- **응답에 있지만 선언되지 않은 필드**: 스키마 드리프트로 간주해 저장을 중단한다.
- **0행 응답**: 필드가 없어야 하며 `totalCount=0`, 실제 행 수 0을 확인한다.

같은 실행에서 `getRegionalTuitionCrntSt`가 설정에 없던 `fieldType3`부터 `fieldType7`까지의
필드를 반환하는 사실도 확인했다. `output_fields`를 실제 응답 구조에 맞게 보완했으며,
값이 없는 `fieldType6`처럼 특정 응답에서 생략되는 필드는 위 부분집합 규칙으로 처리한다.

완전히 동일한 행은 제거하지 않는다. 원문 문자열 기준 행 해시로 중복 수만 계산해
`duplicate_row_count`에 기록한다.

## 7. 저장과 재시작

원본은 다음 경로에 저장한다.

```text
data/raw/academyinfo/{service}/{operation}/{task_id}.xml
```

수집 기록은 `data/metadata/academyinfo_manifest.jsonl`에 한 작업당 한 줄로 추가한다.
각 기록에는 기능 식별정보, 쿼리 없는 출처 URL, 안전한 요청 파라미터, 수집시각, HTTP 및
API 상태, 행·열 수, 실제 필드명, 중복행 수, 파일 크기와 SHA-256이 포함된다.

재시작 절차는 다음 불변조건을 지킨다.

- manifest의 완료 기록과 원본의 경로·크기·SHA-256이 모두 맞아야 건너뛴다.
- 동일 작업 ID에 다른 체크섬이 있으면 충돌로 중단한다.
- 기존 원본 경로는 어떤 경우에도 덮어쓰지 않는다.
- 원본 저장 직후 중단돼 manifest가 없다면 새 응답의 크기와 SHA-256이 같을 때만 기록을
  복구한다.
- 마지막 JSONL 줄이 불완전하면 마지막 정상 위치까지만 복구한다.

원본과 실행 로그는 Git에서 제외한다. manifest는 수집 완료 후 크기와 내용 안정성을
검토한 다음 별도 커밋 여부를 결정하며, 실행 중인 부분 manifest는 코드 커밋에 포함하지
않는다.

## 8. 실행과 운영

`.env`에 `ACADEMYINFO_SERVICE_KEY`를 설정한 뒤 연도를 명시해 실행한다.

```bash
uv run --with pyyaml python scripts/collect_academyinfo.py --year 2025
```

배포 전에는 `--plan-only`, 단일 기능, 단일 학교, `--limit` 순서로 범위를 늘려 확인한다.
장시간 작업은 분리된 세션이나 프로세스 관리 환경에서 실행하고 표준 출력을 로그 파일로
보존한다. 재실행은 같은 명령을 사용하며 별도의 오프셋을 입력하지 않는다.

운영 중에는 다음을 확인한다.

- 프로세스 생존 여부와 로그의 마지막 작업 번호
- manifest 행 수와 마지막 수정시각
- `failed` 유형별 건수와 반복 패턴
- 원본 디렉터리 용량과 남은 디스크 공간
- 새로 등장한 미선언 필드와 API 결과코드 변화

## 9. 오류 처리 원칙

개별 작업의 검증·전송 오류는 안전한 실패 정보로 모으고 다른 작업을 계속 수행한다.
반면 로컬 파일 I/O 오류, manifest 손상, 동일 작업의 체크섬 충돌, 검증 상한 초과는 전체
수집의 신뢰성을 해칠 수 있으므로 즉시 확인한다. 실패 작업은 manifest에 완료로 기록되지
않아 수정 후 같은 명령으로 자동 재시도된다.

스키마 차이가 발생하면 다음 순서로 처리한다.

1. 누락 필드인지 미선언 필드인지 구분한다.
2. 누락 필드는 선택적 태그 생략인지 실제 기능 변경인지 확인한다.
3. 미선언 필드는 실응답과 공식 명세를 대조해 `output_fields`를 보완한다.
4. 단위검사 후 전체 명령을 재실행해 해당 작업이 저장되는지 확인한다.
5. 변경 근거와 관찰일을 문서에 남긴다.

## 10. 테스트 계획

단위검사는 다음 계약을 다룬다.

- 6개 범위 전략의 결정적 작업 생성과 중복 제거
- 고정 파라미터 병합, 비밀키·범위키 충돌 차단
- 재시도, 스트리밍 다운로드, XML 오류와 행 수 검증
- 선택적 필드 생략 허용과 미선언 필드 거부
- 중복행 측정과 원본 보존
- 원자 저장, 무덮어쓰기, 체크섬 검증
- manifest 재개, 불완전 마지막 줄과 고아 원본 복구
- 동시 실행 상한과 실패 격리

코드나 설정을 바꾼 뒤 다음 명령이 통과해야 한다.

```bash
uv run --with pyyaml python -m unittest discover \
  -s tests -p 'test_academyinfo_*.py'
```

실데이터 검증은 2025년 학교목록, 단일 학교·기능, 소규모 `--limit`, 전체 수집 순으로
확대한다. 전체 수집이 끝나면 manifest의 작업 수, 원본 존재 여부, SHA-256, 행 수를 다시
검사하고 실패 작업이 0인지 확인한다.

- XML 프로파일과 응답 계약 검증

- CLI 범위 제한, 계획 전용 실행, 제한된 동시 수집
- 선택적 XML 태그 생략 처리와 등록금 지역통계 스키마 보완

- 2025년 17,431개 작업 전체 완료
- 수정 후 재시도한 기존 실패 작업의 정상 저장
- 전체 로그에서 남은 실패 유형 분류 및 설정 보완

### 완료 기준

2025년 계획의 모든 작업이 완료 manifest에 정확히 한 번 나타나고, 각 원본의 크기와
SHA-256 및 XML 행 수가 기록과 일치하며, 인증정보가 저장 산출물과 로그에 없을 때 1차
수집을 완료로 판단한다. 예외가 남으면 작업 ID, 오류 유형, 재현 조건과 후속 결정을 별도
품질 기록에 남긴다.
